# 6.7 — The limits the spec says must not be sent or accepted

**Workstream:** 6 — Testing
**Context:** [specifications.html](../specifications.html) §Marshalling containers
**Requires:** none — additions to `dbus_marshaller`
**State:** draft

## What

Three of the spec's hard limits are phrased as "implementations must not send or accept", and
`dbus_marshaller` enforces none of them. The property suite cannot notice, because every
generator stays comfortably inside them: `short_list/1` caps collections at four elements and
`messages/0` at four messages, both for memory reasons that have nothing to do with the
protocol.

**Array length** — §Marshalling containers caps an array's data at 2²⁶ bytes (64 MiB).
`unmarshal_array/5` takes the `uint32` off the wire and counts down from it, so a peer that
writes 4 GiB puts the decoder into a loop bounded only by how much buffer arrives. It
degrades to `more` rather than looping forever, but the cap is the documented defence and it
is absent.

**Message length** — §Message Format caps a whole message at 2²⁷ bytes (128 MiB).
`unmarshal_header_fields/2` trusts the header's `size` field to slice the body out, so this
is the length that decides how much a peer can make us buffer before we will look at
anything. This is the one that matters for a library that reads off a socket.

**Object paths** — §Valid Object Paths: "Implementations must not send or accept messages
with invalid object paths", then five rules (leading `/`, elements of `[A-Za-z0-9_]`, no
empty element, no `//`, no trailing `/` except the root). `marshal/3` forwards `object_path`
straight to the `string` clause ([dbus_marshaller.erl:238](../../src/dbus_marshaller.erl#L238))
and `unmarshal/4` does the same, so nothing is checked in either direction. The generator
produces only valid paths — and only lowercase ones, which is its own narrowing, filed in
[6.2](6_2.md).

Enforcing a limit is not free: a check on the decode path runs on every message. The array
and message caps are two comparisons against a constant and belong there. Object-path
validation is a scan of the bytes, so it goes on the **encode** side unconditionally — we
must not *send* one — and on the decode side it is worth stating as a property against a
generator of invalid paths even if the check itself is left to the layer above; say which was
chosen and why in the code, because "we validate paths" and "we validate paths we send" are
different promises to a caller.

## Checklist

- [ ] Reject an array whose length word exceeds 2²⁶ on decode, and an encoded array that
      would exceed it, with a named error.
- [ ] Reject a header `size` that would take the message past 2²⁷ before slicing the body.
- [ ] `dbus_marshaller:is_valid_object_path/1` implementing the five rules; called from
      `marshal/3`'s `object_path` clause.
- [ ] `dbus_marshaller_gen:invalid_object_path/0` — empty, no leading slash, `//`, trailing
      slash, an element with `-` or `.` in it, and a non-UTF-8 byte.
- [ ] `prop_object_path_validation`: every path from `object_path/0` marshals, every path from
      `invalid_object_path/0` is rejected.
- [ ] Widen `object_path/0` to include `[A-Z]`, closing the unmarked narrowing recorded by
      [6.2](6_2.md).

## Acceptance

- [ ] A hand-built message whose array length word is `16#4000001` is `{error, _}` from
      `unmarshal_data/1`, not `more`.
- [ ] A header claiming a body of 2²⁷ bytes is rejected without the decoder buffering toward
      it.
- [ ] `marshal(object_path, <<"/foo/">>, 0)` and `marshal(object_path, <<"foo">>, 0)` are
      errors; `marshal(object_path, <<"/">>, 0)` and `<<"/Foo/Bar1">>` are not.
- [ ] `prop_object_path_validation` passes at `-n 5000`, and `prop_value_roundtrip` is
      unaffected.

# 7.2 — Fd-aware transport send and recv

**Workstream:** 7 — Unix FD passing
**Context:** [dbus-unix-fd-passing.md](../dbus-unix-fd-passing.md) §Transport API
**Requires:** none — `m:dbus_transport` only
**State:** draft

## What

`m:dbus_transport` moves bytes. To carry descriptors it needs `socket:sendmsg/4` and
`socket:recvmsg/5` instead of `socket:send/2` and `socket:recv/4`, and an API that has
somewhere to put them: `send/3` taking a descriptor list, `recv/2` returning one.

**This is not a new behaviour callback**, though §Transport API used to propose two. The
three transport modules do not own their I/O — since "Simplify transport" they own `connect/1`
and nothing else, and `send`, `recv` and `close` live once here against the
`t:socket:socket/0` all three return. Callbacks would put two functions back into each
module, and `nonce-tcp` would delegate both to `m:dbus_transport_tcp`, which is exactly the
delegation just deleted from it. The distinction that matters is not `unix` versus `tcp` but
fd-capable versus not, and that is already a boolean on the connection —
`#transport.support_unix_fd`, filled at `connect/1` from the module's `support_unix_fd/0`.
Two clauses on that field, in one module.

The transport is *not* told the negotiation result. `support_unix_fd` says the socket can
carry descriptors; `AGREE_UNIX_FD` says the peer agreed that it may. The second belongs to
`m:dbus_connection` ([7.3](7_3.md)), which is also the layer that writes and reads `UNIX_FDS`.
Here, a non-empty descriptor list on a transport that cannot carry one is
`{error, unix_fd_not_supported}` and nothing more.

Two things `socket:send/2` did that `socket:sendmsg/4` does not. It looped: `sendmsg` answers
`{ok, RestData}` or `{error, {Reason, RestData}}` on a partial write, and the descriptors
have already gone with the first byte, so the remainder must be resent *without* the control
message or the peer receives them twice. And it needed no payload: `SCM_RIGHTS` with an empty
`iov` is not delivered on Linux — never a problem for a D-Bus message, which is at least
sixteen bytes, but it is why descriptors cannot be flushed on their own.

On the receiving side the control buffer is sized by the caller and overflowing it *loses*
descriptors: the kernel truncates the ancillary data, closes what it dropped, and says so
only through `ctrunc` in the returned flags. That is a protocol error, not a short read.

OTP hands `rights` over undecoded — `t:socket:cmsg_recv/0` types it `data := binary()` with
no `value` field, unlike `timestamp` — so the payload is an array of native C `int`s and the
codec is two comprehensions over `32/native-signed`.

`dbus_transport_unix:support_unix_fd/0` stays `false` for now. Nothing on the wire changes
until [7.4](7_4.md) flips it; this issue is the code underneath.

## Checklist

- [ ] `send/3` taking `[fd()]`; keep `send/2` as `send(Conn, Data, [])` — the opening NUL
      byte and the whole SASL conversation have no descriptors to pass.
- [ ] `send/3` on a transport with `support_unix_fd = false`: `socket:send/2` for an empty
      list, `{error, unix_fd_not_supported}` for a non-empty one.
- [ ] `send/3` with descriptors: one `rights` control message, then loop on `{ok, Rest}` and
      `{error, {Reason, Rest}}` resending `Rest` with no `ctrl`.
- [ ] `recv/2` returns `{ok, Data, Fds}`; `socket:recv/4` and `[]` when the transport cannot
      carry descriptors, `socket:recvmsg/5` when it can.
- [ ] `?MAX_UNIX_FDS` (16) and a control buffer sized for it; treat `ctrunc` in the returned
      flags as `{error, fd_truncated}`.
- [ ] Concatenate every `rights` message in `ctrl`, in order — one `recvmsg` may return
      several.
- [ ] `encode_fds/1` and `decode_fds/1` over `32/native-signed`; a payload whose size is not
      a multiple of four is `{error, {bad_rights, Size}}`, not a descriptor list.
- [ ] Update the two callers of `recv/2`: `dbus_auth_client_mech:do_recv/1` and
      `dbus_connection:reader_loop/2`, plus the `roundtrip` eunit tests in the three
      transport modules.
- [ ] Drop the `socket:setopt(Sock, {otp, meta}, #{unix_fd => true})` in
      `dbus_transport_unix:connect_socket/2` and the paragraph of the moduledoc that explains
      it: it was the store for the removed `disable_unix_fd/1`, and nothing reads it.

## Acceptance

- [ ] `rebar3 eunit` passes; the transport round-trip tests exercise `send/3` and the
      3-tuple `recv/2`.
- [ ] Over a `socketpair`, a descriptor sent with `send/3` arrives as a *different* number on
      the other side that names the same open file — `socket:open/2` on it, on a socket
      descriptor, reaches the same peer.
- [ ] `send/3` with descriptors on a TCP connection is `{error, unix_fd_not_supported}` and
      writes nothing; with `[]` it is indistinguishable from `send/2`.
- [ ] `recv/2` on a TCP connection returns `{ok, Data, []}`.
- [ ] Sending 17 descriptors in one call is refused before the `sendmsg`.
- [ ] A payload large enough to be written partially still arrives once, with its descriptors
      delivered exactly once — assert the received count, not just success.
- [ ] `decode_fds(<<0, 0, 0>>)` is an error rather than a one-element list.

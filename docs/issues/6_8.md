# 6.8 — Generator defects at the boundaries

**Workstream:** 6 — Testing
**Context:** [specifications.html](../specifications.html) §Valid Signatures
**Requires:** [6.2]
**State:** draft

## What

Four small defects in the property suite itself. None of them makes a passing property wrong
today; each makes it weaker, or leaves a trap for whoever changes a generator next.

**A signature can be generated one byte over the limit.** `signature/0` bounds the encoded
form with `?SUCHTHAT(…, byte_size(sig_bin(Sig)) =< 255)`
([dbus_marshaller_gen.erl:133](../../test/dbus_marshaller_gen.erl#L133)) and then
`guarded_sig_and_values/0` ([:222](../../test/dbus_marshaller_gen.erl#L222)) appends a
`uint64`, which can take it to 256. `marshal_string(byte, …)` writes that length through
`marshal(byte, 256, _)`, whose `255 >= Value` guard fails, and the call falls through to
`error({marshaling, byte, 256})`. It is unreachable in practice — a draw of one to four types
of bounded size is nowhere near 255 bytes — but the bound belongs after the guard element,
not before it, and the same signature is written into the `SIGNATURE` header field by
`message/0`.

**The empty signature is never generated.** `signature/0` draws `integer(1, 4)` types. §Valid
Signatures defines a signature as "zero or more single complete types";
`marshal_signature([])` and `unmarshal_signature(<<>>)` both handle the empty case, and it is
the signature of every no-argument message. `value(signature)` inherits the same floor, so
the empty signature is never carried as a *value* either — the `<<0, 0>>` encoding, which is
the one a `g` field most often holds in practice.

**`prop_never_crashes` uses `catch`.** A bare `catch` returns a *thrown* term unchanged, so a
`throw(more)` from inside the decoder would satisfy the property rather than fail it. That is
not hypothetical shaped: `unmarshal_data/2` has a `catch {'EXIT', Err} ->` clause, which
catches a throw of that tuple and tells you someone once expected this code to throw.
`try … catch _:_ -> false end` says what the law means.

**`prop_endian_agreement` discards its position.** It draws
`{Type, Value, _Pos}` from `fixed_width_typed_value/0` and then encodes at 0, with a comment
explaining that no type is padded there. The comment is right, but the generator is then
doing work whose result is thrown away, and the property reads as if it covered offsets when
it does not — the offsets it needs come from [6.4](6_4.md)'s independent alignment table.

## Checklist

- [ ] Apply the 255-byte bound in `guarded_sig_and_values/0`, after the guard element is
      appended.
- [ ] Let `signature/0` and `value(signature)` produce the empty signature; check
      `prop_signature_roundtrip` and `prop_value_roundtrip` still hold for it, since
      `unmarshal_tuple/3`'s clause guard is `byte_size(Data) > 0`.
- [ ] Replace the `catch` in `prop_never_crashes` with `try … catch _:_ -> false end`.
- [ ] Give `prop_endian_agreement` a generator that does not draw a position, and say in the
      moduledoc that it is an offset-0 law.
- [ ] `lax/2` descends into containers, so an iolist inside a struct or an array of strings
      reaches the permissive clauses of `marshal/3`; today only the top-level value is laxed.

## Acceptance

- [ ] `rebar3 proper -n 5000` passes with all five changes.
- [ ] A signature of exactly 255 bytes plus the guard element is either not generated or
      marshals; neither raises.
- [ ] `prop_value_roundtrip` reports `[]` among its aggregated type shapes.
- [ ] Making `unmarshal_data/1` `throw(more)` on some input fails `prop_never_crashes`, where
      today it passes.

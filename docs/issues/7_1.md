# 7.1 — The `h` type and the `UNIX_FDS` header field

**Workstream:** 7 — Unix FD passing
**Context:** [specifications.html](../specifications.html) §Summary of types
**Requires:** none — additions to `dbus_marshaller`
**State:** draft

## What

`UNIX_FD` is the one basic type `m:dbus_marshaller` does not know. `type_code/1` answers
`error` for `$h`, so any signature containing one is `{bad_signature, {bad_type_code, 104}}`
and the message is refused before anything else in this workstream can matter. Nothing about
descriptors is involved: on the wire an `h` is a `UINT32` with four-byte alignment, and the
work here is the six one-line tables it is missing from.

**The value of an `h` is an index, not a descriptor.** §Summary of types calls it "32-bit
index into the array of file descriptors that accompany the message". Keeping that literal is
what lets `marshal/3` stay stateless: an fd-valued `h` would mean threading an accumulator
through all forty of its clauses and changing the return type of every one, to buy an
abstraction the message layer can offer for free on top. GDBus and `sd-bus` both expose the
index and a separate descriptor list for the same reason.

The descriptors themselves ride on `#dbus_message{}`, in a new `fds` field, and the count
goes in header field 9. `marshal_message/1` already synthesises the `SIGNATURE` field rather
than trusting the caller — `UNIX_FDS` is the same case and gets the same treatment, so a
caller sets `fds` and never the field. `marshal_message/1` keeps returning a `binary()`: the
descriptors are on the record the caller already holds, and `m:dbus_connection` reads them
from there when it calls the transport, so no signature has to grow a tuple.

Decoding is where the count is spent, and it needs the queue that [7.3](7_3.md) owns, so this
issue adds `unmarshal_data/2` — the same function with a descriptor queue in and out — and
leaves `unmarshal_data/1` as `/2` with an empty one. That keeps the property suite, which
calls `/1` several thousand times a run, unchanged; `extra_fields/0` never generates field 9,
so no generated message reaches the new path by accident.

The per-message limit is checked here, on the header, before anything is allocated against
it: `libdbus` allows 16 descriptors per message, and `dbus-daemon` publishes the number as
`max_message_unix_fds` — `/usr/share/dbus-1/system.conf:118` carries the stock value,
commented out, at 16.

## Checklist

- [ ] `dbus.hrl`: add `unix_fd` to `dbus_type()`, `-define(FIELD_UNIX_FDS, 9)`, and
      `fds = [] :: [non_neg_integer()]` on `#dbus_message{}`.
- [ ] `dbus_marshaller`: `signature_bytes(unix_fd) -> "h"`, `type_code($h) -> {ok, unix_fd}`,
      `padding(unix_fd) -> 4`, `marshal(unix_fd, …)` with the `uint32` range guard, and
      `unmarshal(unix_fd, …) -> unmarshal_uint(4, …)`.
- [ ] Leave `basic_type_code/1` deriving from `type_code/1`: `h` is a basic type, so it is a
      legal dict key, and only `v` is excluded.
- [ ] `marshal_message/1`: emit `{?FIELD_UNIX_FDS, #dbus_variant{type = uint32, value = N}}`
      when `fds` is non-empty, in both the `body = undefined` and the body clauses.
- [ ] Refuse to marshal a message carrying more than `?MAX_UNIX_FDS` (16) descriptors.
- [ ] `unmarshal_data/2`: take and return a descriptor queue; per message, read `UNIX_FDS`,
      take that many off the front into `#dbus_message.fds`, and answer `more` when the
      message is byte-complete but the queue is short — the descriptors are still in flight.
- [ ] Refuse `UNIX_FDS` above `?MAX_UNIX_FDS` as `{error, {too_many_fds, N}}`.
- [ ] `unmarshal_data/1` = `unmarshal_data(Bin, [])`, returning the 3-tuple it returns today.
- [ ] `dbus_message:fd/2`: resolve an index against `#dbus_message.fds`, `{error, {bad_fd_index, I}}`
      out of range. Index validation happens here, not by scanning bodies for `h` values.
- [ ] `dbus_marshaller_gen`: add `unix_fd` to `basic_type/0` and the `type/1` leaf union,
      `value(unix_fd)`, `alignment(unix_fd) -> 4`, `fixed_width(unix_fd)`.

## Acceptance

- [ ] `rebar3 proper -n 5000` passes, and `prop_value_roundtrip` reports `unix_fd` among its
      aggregated type shapes.
- [ ] `marshal_signature([unix_fd])` is `<<"h">>` and `unmarshal_signature(<<"h">>)` is
      `{ok, [unix_fd]}`; a `{dict, unix_fd, string}` signature round-trips.
- [ ] An `h` marshals byte-for-byte as the `u` with the same value at the same offset, at
      offsets 0 through 7.
- [ ] A message with `fds = [3, 4]` marshals with header field 9 present and equal to 2, and
      the caller did not set that field.
- [ ] `unmarshal_data(Bin, [3, 4])` on those bytes gives back a message with `fds = [3, 4]`
      and an empty remaining queue; `unmarshal_data(Bin, [3])` answers `more`.
- [ ] A header claiming `UNIX_FDS` of 17 is `{error, {too_many_fds, 17}}`, with no attempt to
      take 17 descriptors off a shorter queue.
- [ ] `dbus_message:fd(2, Msg)` on a message with two descriptors is `{error, {bad_fd_index, 2}}`.

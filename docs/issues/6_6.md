# 6.6 — Message shapes the wire properties cannot reach

**Workstream:** 6 — Testing
**Context:** [specifications.html](../specifications.html) §Header Fields
**Requires:** [6.5]
**State:** draft

## What

`dbus_marshaller_gen:message/0` generates exactly one shape: little-endian, a `SIGNATURE`
header field always present, and a body of two or more arguments. Three decoder paths are
therefore unreachable from `prop_dbus_marshaller_wire`, and one of them is the commonest
message on a real bus.

**No body.** §Header Fields makes `SIGNATURE` optional: "If omitted, it is assumed to be the
empty signature (i.e. the body must be 0-length)". `marshal_message/1` has a dedicated
`body = <<>>` clause and `unmarshal_message/1` returns `body = undefined` when the field is
absent, erroring `body_parse_error` if a body turns up anyway. That is a method call with no
arguments — most of the traffic — and it is also the only shape where
[6.5](6_5.md)'s body type is uncontroversial. The generator never produces it because
`guarded_sig_and_values/0` always appends a `uint64`.

**One argument.** `unmarshal_body/4` unwraps a one-element tuple
([dbus_marshaller.erl:468](../../src/dbus_marshaller.erl#L468)), so a single-argument body
decodes to a **bare value**, not a 1-tuple. That asymmetry is exactly the kind of thing the
`canon/2` machinery exists to state, and it is stated nowhere. It does not need `BUG-4` fixed
first: the 8-byte guard is only needed when a *struct* lands near the end of the buffer, so a
one-element signature drawn from the struct-free types reaches this clause today.

**Big-endian.** `marshal_message/1` hardcodes `$l`, so `unmarshal_header2/2`'s `$B` clause
and the whole big-endian path for strings, arrays, structs and variants are never
round-tripped. `prop_endian_agreement` covers the nine fixed-width types at offset 0 only —
and discards the `Pos` its generator draws. The only `$B` bytes the suite ever produces are
accidental flips of byte 0 in `corrupted_stream/0`, which land in `prop_never_crashes` where
any `{error, _}` is a pass. A decoder-only big-endian law is stateable without touching the
encoder: byte-swap each field of a marshalled message and require the two decodes to agree.

Unrelated but in the same function, and cheap to clear while there:
`unmarshal_header_fields/2`'s second clause
([:498](../../src/dbus_marshaller.erl#L498)) matches a 7-element list against the result of
`unmarshal({array, {struct, [byte, variant]}}, …)`, which is a list of `{Code, Value}` pairs
and never has that shape. It is dead. The `more` check it was meant to perform is done
correctly by the clause below it.

## Checklist

- [ ] `dbus_marshaller_gen:empty_message/0`: no `SIGNATURE` field, `body = <<>>`, expected
      decode `body = undefined`; folded into `message/0`'s union and into `messages/0`, so
      the incremental-decode law sees a stream mixing both shapes.
- [ ] `prop_single_argument_body_unwraps`: for a one-element signature over the struct-free
      types, the decoded body is the value, not a 1-tuple.
- [ ] A case for the rejected shape: a non-empty body with no `SIGNATURE` field is
      `{error, body_parse_error}`.
- [ ] `prop_big_endian_message`: a marshalled message with every multi-byte field byte-swapped
      and the endian byte set to `$B` decodes to the same message as the little-endian
      original.
- [ ] Delete the dead clause at `unmarshal_header_fields/2`.

## Acceptance

- [ ] `rebar3 proper --cover` shows `unmarshal_body/4`'s `{ok, {}, …}` and `{ok, {Body}, …}`
      clauses covered, where they are cold today.
- [ ] A `METHOD_CALL` with `PATH` and `MEMBER` and no body round-trips, and appears in a
      multi-message stream in `prop_incremental_decode`.
- [ ] `prop_big_endian_message` passes at `-n 1000` and fails if `unmarshal_uint/4`'s `$B`
      branch is changed to little-endian.
- [ ] Deleting the dead clause changes no test result.
